# teachloop-skills

把实际教学产品中形成的设计判断，整理成可以继续使用的 AI skills。

第一个 skill 来自我为一对一英语教学开发的微信小程序（[朱老师英语课堂](https://github.com/ZIzi821/Teaching-Students-English-Program)）：开发中反复用到的判断（谁来确认完成、什么算学习证据、孩子下一步做什么、状态怎么流转）散在代码、测试和交接文档里，整理成 skill 后，用 AI 助手开发新功能或新产品时不必每次重新说明。

每个 skill 使用一个独立子目录，目录中以 `SKILL.md` 为入口；以后新增技能沿用相同结构。

## 当前技能

| Skill | 用途 | 入口 |
| --- | --- | --- |
| `teacher-led-learning-design` | 教师主导的语言学习产品设计与迭代：学习证据、角色职责、下一步行动和个性化复习 | [SKILL.md](teacher-led-learning-design/SKILL.md) |

结构：入口 `SKILL.md` 写触发描述、决策原则和“按任务读取哪份参考”的路由表；5 份参考（教学原则、流程与证据、界面与文案、项目契约、修改与交付）按需加载。

## 评测结果

[评估目录](evaluations/teacher-led-learning-design/) 保存场景与本次验证结果，和技能本体分开维护。入口、YAML、引用文件、公开内容检查与行为评估承担不同验证目的。

- **8 个行为场景**：首页加统计卡、新学生没有观察数据、提交后被重复催交、成人产品自行确认完成、AI 录音分析、教师预览、错题与板书分流、刷选择题后延长复习。期望答案只用于评审，不提供给执行者。
- **3 个不应触发的请求**：排版作业 PDF、查询微信 API、修改简历，用来检查触发边界。
- **独立执行**：两组独立执行各完成 4 个场景，只拿到 skill 入口和需求，不读案例文件、不访问原项目。
- **结果**：8 个场景的设计输出全部符合期望。首轮“教师预览”场景提出新增预览上传区，暴露约束写得不够明确；把“预览默认本地演练、不上传录音、不新增预览后端”补进流程参考和项目契约，只重跑这个场景，复测通过。
- **局限**：这是人工语义评审，说明当前规则在这些情境下能产出符合预期的设计；不是可重复的模型准确率统计，也没有在宿主的自动选择机制里实测触发率。

## 使用

让支持 skill 文件的助手读取目标目录的 `SKILL.md`，再提出具体任务，例如：

```text
请读取 teacher-led-learning-design/SKILL.md，
按它的方法设计一个帮助老师处理课后录音的页面。
先给出角色、关键状态、页面内容和处理后的去向。
```

安装到所用工具的技能发现目录后，可以使用 `$teacher-led-learning-design` 调用。此仓库保存技能源文件；是否已安装和当前工具能否发现，要以实际环境为准。

核心方法和项目适配分别存放。用于其他教学产品时，沿用其本身的代码、身份和发布约定；只有明确匹配原小程序时才加载其项目契约。

## 维护

更新 skill 时修改拥有对应规则的文件，避免复制完整交接和重复维护常量。使用合成示例，保留数据来源及授权边界，不收录真实学生记录或私密配置。
